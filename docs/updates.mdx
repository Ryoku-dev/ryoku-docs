Ryoku updates through one command, `ryoku update`, or **Update now** on
**Ryoku Settings > Updates**. It brings the Ryoku packages current from the
signed Ryoku repository for your edition (pacman, XBPS or RPM), re-lays the base
config with `ryoku materialize`, runs `ryoku doctor`, and reloads the shell.
When the system meets the snapshot prerequisites, the run is wrapped in a
snapper pre and post snapshot.

This page covers the update and snapshot model. The full `ryoku` command
reference (every flag for `update`, `status`, `track`, `snapshots`, `rollback`,
`doctor` and `recovery`) lives in [CLI](/docs/cli).

## Two lanes

| Lane | Command | What moves |
|---|---|---|
| **Ryoku** | `ryoku update` | Ryoku's packages from its signed repository, then config and doctor |
| **Your distribution** | `sudo pacman -Syu` (Arch, CachyOS), `sudo xbps-install -Syu` (Void), `sudo dnf5 upgrade --refresh` (Fedora) | the base system and its kernel |

`ryoku update` never moves the kernel or the distribution base on its own: a
Ryoku release stays reversible, and a box that cannot take a distribution
upgrade today can still take a Ryoku fix. Every run reports how many
distribution packages are waiting, and the Updates page lists them.
`ryoku update --system` runs both lanes under one snapshot pair when you want
that; on Void it is the way to keep base updates covered by snapshots.

## Channels

| Channel | What it follows |
|---|---|
| **stable** | named releases, as signed packages (the default) |
| **unstable** | the `unstable-dev` branch, fast-forwarded to the last commit the Testing gate passed |

`ryoku track unstable` moves a box to the unstable channel and
`ryoku track stable` brings it back. `ryoku track <version>` pins one frozen
release or unstable build, and `ryoku rollback --to <version>` moves the Ryoku
package set to one without a reboot.

## What `ryoku update` does

1. Take a snapper pre-snapshot (best-effort; an unconfigured snapper never
   blocks the update).
2. Upgrade the installed Ryoku packages from the signed Ryoku repository.
3. `ryoku materialize` to re-lay Ryoku's base config under `~/.config`. Your own
   edits live in `~/.config/ryoku/user_edits` and survive every update.
4. `ryoku doctor` to reconcile stateful drift. It also installs, once, an app
   Ryoku now ships by default that this box has never had; an app you removed
   stays removed.
5. Reload the shell.
6. Take a snapper post-snapshot.

Throughout, progress is published to `$XDG_RUNTIME_DIR/ryoku-update.json`,
which the shell's update island reads to show the run in the bar.

```bash
ryoku update
```

## Status

`ryoku status` is read-only. It prints the active config base, the installed
`ryoku-desktop` version, what the `[ryoku]` repo offers, the count of pending
package updates (via `checkupdates` from `pacman-contrib`), and the snapshot
count.

```bash
ryoku status
```

The `--json` form is the data seam the Hub and the update island read; it is
not meant for humans.

## Snapshots and rollback

When the system meets the prerequisites, every `ryoku update` is wrapped in a
snapper pre/post snapshot pair. The prerequisites are a btrfs root with a
snapper `root` config that writes snapshots to the `@snapshots` subvolume at
`/.snapshots`. The standard ISO install sets all of this up, so on a normal
install the safety net is on from first boot.

It is best-effort by design. On a non-btrfs root, or on a machine where the
snapper `root` config is missing, `ryoku update` proceeds without a snapshot
rather than refusing to update. `ryoku doctor` runs inside every update and,
on a btrfs root with the `root` config missing, creates the config from the
same template the installer uses, registers it in `/etc/conf.d/snapper`,
fixes `/.snapshots` ownership, and enables the cleanup timer, so a drifted
or partially installed machine self-heals on the next run. On a non-btrfs
root, snapshots stay unavailable.

To see what you have:

```bash
ryoku status
ryoku snapshots
```

`ryoku status` prints the snapshot count; `ryoku snapshots` lists them, and
fails clearly when snapper is not configured. If it prints `The config 'root'
does not exist`, see [Troubleshoot](/docs/troubleshoot) for the exact
recovery path.

To roll back, pass an id; with no id, `ryoku rollback` lists them so you can
pick one. The same snapshots are selectable from the Limine boot menu when
`limine-snapper-sync` is installed and snapshots exist, so a truly broken
system can be recovered from the bootloader.

```bash
ryoku rollback
ryoku rollback 42
```

This hands off to `sudo snapper rollback`.

## Self-healing: `ryoku doctor`

`ryoku doctor` runs idempotent reconcilers for the stateful drift that packages
and config cannot express. A healthy machine is quiet. It runs inside every
`ryoku update`, so you rarely call it by hand; `ryoku doctor --check` previews
what it would change without touching anything.

```bash
ryoku doctor --check
```

For the full reconciler set and every doctor flag (`--check`, `--report`, and
the opt-in, read-only `--explain`), see [CLI](/docs/cli). To lean on doctor
while chasing a specific problem, see [Troubleshoot](/docs/troubleshoot).

## Recovery

When the desktop is too broken to update normally (a half-applied upgrade, a
corrupt config, a broken local build), `ryoku recovery` is the last resort. It
always restores the stable channel: it pulls `main`, reinstalls the base
packages and redeploys the desktop, overwriting Ryoku's configs. It hands off to
`bin/ryoku-recovery`, preferring a local copy and otherwise fetching the
canonical script over the network, so it still works when the local install is
broken.

```bash
ryoku recovery
```

If even the graphical session is gone, drop to a TTY (`Ctrl+Alt+F2`), log in,
and run `ryoku rollback` or `ryoku recovery` from there. The Limine boot menu
offers the same snapper snapshots if the disk itself still boots.

## Where the packages come from

The desktop ships as signed packages from the Ryoku repository for each
edition: pacman on Arch and CachyOS, XBPS on Void, RPM on Fedora.
`ryoku-desktop` is the umbrella package; the installer adds the repository,
imports the release key, installs `ryoku-desktop` and the variant for your
window manager, and from then on `ryoku update` keeps the machine current.
Apps you left out at install time are recorded and never added back.

Because every Ryoku package is signed and verified on install, an update only
ever applies packages from the real release key. See
[Security](/docs/security) for how to verify releases yourself.

## State the CLI keeps

The CLI keeps its state under `~/.local/state/ryoku/`: the `materialized`
manifest of Ryoku-owned files, the `provisioned` ledger of apps delivered or
left out, and the latest `doctor-report.txt`. During a run it publishes live
progress to `$XDG_RUNTIME_DIR/ryoku-update.json` for the bar's update island.
See [CLI](/docs/cli) for the full list.
