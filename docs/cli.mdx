`ryoku` is the front door to the whole system. It updates the machine, moves it
between channels, rolls it back, reports its state, reloads the desktop and
repairs stateful drift, all from one Go program (`ryoku/cli/`). It does not
reimplement package management or snapshots: it drives pacman, XBPS or DNF and
snapper, and adds the safety rails around them. Run `ryoku help` for the
built-in usage.

## Two worlds

Every command behaves with respect to one of two ways Ryoku can live on a
machine.

<Tabs>
  <Tab title="Packaged install (normal)">
    The desktop is installed from Ryoku's signed repository with pacman, XBPS
    or DNF. `ryoku-desktop` ships the base config under
    `/usr/share/ryoku/config`; there is no git checkout and no build toolchain.
    This is what the ISOs and the script installer give you.
  </Tab>
  <Tab title="Source checkout (unstable, maintainers)">
    The desktop is built from a checkout of the repository and laid down by
    `ryoku/shell/deploy.sh`. `ryoku track unstable` sets this up for testers;
    the deploy records the checkout and the commit it laid down under
    `~/.local/state/ryoku/`, which is how `ryoku` finds it again.
  </Tab>
</Tabs>

`ryoku update` detects which world it is in, so the same command is correct on
both.

## At a glance

| Command | What it does |
| --- | --- |
| `update` | Snapshot where supported, then bring Ryoku current, re-lay config, run doctor, reload |
| `status [--json]` | Channel, installed and latest version, waiting system packages, snapshot count |
| `track <channel-or-version>` | Follow `stable` or `unstable`, or pin one release or build |
| `rollback [id]` | List releases and snapshots; `--to <version>` moves back to a release |
| `snapshots` | List the root snapshots where the edition provides them |
| `reload` | Restart the shell and reload the window manager |
| `reset [path]` | Drop one of your Ryoku Settings overrides, back to the default |
| `owner <path>...` | Who writes a config file, and where your change belongs |
| `doctor` | Run the idempotent reconcilers for stateful drift |
| `wm` | The window-manager seam: `status`, `caps`, `use <name>` and more |
| `plugin` | Create, validate, add, remove or share a shell plugin |
| `keyboard` | One keyboard layout on the desktop, greeter, console and disk prompt |
| `keyring` | How the login keyring unlocks at sign-in |
| `security-key` | Enroll a FIDO2/U2F key for sudo, polkit or login |
| `import <path>` | Bring in an existing dotfiles tree, with undo |
| `recovery` | Last resort: restore the stable channel and redeploy |

## Everyday commands

### `ryoku update`

The full, safe update. Where the edition supports snapshots it is wrapped in a
snapper pre and post pair; an unconfigured snapper never blocks the update, but
a failed step aborts before anything else changes.

On a packaged install it moves the packages Ryoku's signed repository serves,
by name, then lays the refreshed config in with `ryoku materialize`, runs
`ryoku doctor` and reloads the shell. It leaves your distribution's own
upgrade (`sudo pacman -Syu`, `sudo xbps-install -Syu`, `sudo dnf5 upgrade
--refresh`) to you and reports how many of those packages are waiting. On a
source checkout it fast-forwards to the last commit that passed the Testing
gate and redeploys.

| Flag | What it does |
| --- | --- |
| `--system` | Also run the distribution upgrade, under the same snapshot pair. |
| `--wait` | Wait for a channel build or source check that is still running. |
| `--force` | Update despite a build or check in progress. |
| `-v`, `--verbose` | Stream the raw output instead of the summary. |
| `--gui` | Run in the background, driven from the Updates page of Ryoku Settings. |

On a terminal the run is a short console: one line per step, a progress bar and
a closing card. Everything the tools print goes to
`~/.local/state/ryoku/update-log.txt`; on failure the card shows the error and
the last lines, and offers the pre-update snapshot. Progress is also published
to `$XDG_RUNTIME_DIR/ryoku-update.json` for the bar's update island. See
[Updates](/docs/updates) for the model.

### `ryoku status [--json]`

A read-only report. It prints the active config base, the installed
`ryoku-desktop` version, what the signed repository offers, and the waiting
distribution packages as `system:`. A source checkout shows the channel, the
deployed commit and how far behind it is. When the channel is still building
or its last build failed, a `build:` line says so. `--json` is the data seam
the Hub and the update island read.

### `ryoku track <channel-or-version>`

`stable` follows named releases as signed packages. `unstable` builds the box
from the `unstable-dev` branch and, from then on, `ryoku update` fast-forwards
to the last commit the Testing gate passed. A release tag or an unstable build
name pins that frozen version as packages. `ryoku track stable` returns a box
to packages. The package managers move channels in one transaction and restore
the previous repository if the move fails.

### `ryoku rollback [id]`

With no arguments it lists published releases and, where the edition supports
them, local snapshots. `ryoku rollback --to <version>` moves the Ryoku package
set to a frozen release without a reboot; the distribution base and kernel do
not move. After such a move the boot guard watches the next boots and moves the
Ryoku set back if two boots fail to reach a healthy desktop.

`ryoku rollback <id>` walks you through a whole-system restore:

<Tabs>
  <Tab title="Arch, CachyOS, Void">
    Reboot, choose **Ryoku Linux > Snapshots > id** in the Limine menu, run
    `sudo limine-snapper-restore`, then reboot into the restored system.
  </Tab>
  <Tab title="Fedora">
    The snapshots are under **Ryoku snapshots** in GRUB (hold Shift or press Esc
    while booting). A snapshot boots read-only; to keep it, run
    `sudo ryoku boot-menu restore` in that boot.
  </Tab>
</Tabs>

### `ryoku snapshots`, `ryoku reload`, `ryoku reset`

- `ryoku snapshots` lists the root snapshots on editions that provide them.
- `ryoku reload` restarts the shell and reloads the window manager. Use it after
  a hand edit to config that is already in place.
- `ryoku reset [path]` drops an override from `~/.config/ryoku/user_edits`, so
  that file goes back to the Ryoku default. With no path, and after a confirm,
  it drops them all.

### `ryoku owner <path>...`

Answers the question to ask before touching a config file: who writes it, and
where your change belongs so an update does not overwrite it.

```text
$ ryoku owner ~/.config/kitty/kitty.conf
/home/you/.config/kitty/kitty.conf
  class:   ryoku
  writer:  the ryoku-desktop package, through materialize
  advice:  Ryoku ships this and overwrites it on every update. Put your change in ~/.config/kitty/user.conf instead.
  edit:    /home/you/.config/kitty/user.conf
```

`--json` prints the same for a tool, and `--map` prints an ownership summary of
the whole machine.

## Keep it healthy: `ryoku doctor`

`ryoku doctor` runs the convergent reconcilers: idempotent checks (and, where it
is safe, fixes) for stateful drift the package and config layers cannot express.
A healthy machine is quiet.

```bash
ryoku doctor            # heal what is safe to heal
ryoku doctor --check    # or -n: show what is wrong, change nothing
ryoku doctor --verbose  # also list the checks that passed
```

<Note>
  `ryoku update` runs `ryoku doctor` for you, so a finding never aborts an
  update. Ryoku Settings shows the same findings as a system check.
</Note>

The reconcilers live in `ryoku/cli/internal/doctor/` and cover desktop
sessions, channel health, the keyring, compositor config, displays and
backlights, pending package config, orphaned packages, duplicate launcher
entries and more, with host-specific checks on each edition. Each one retires
once every supported install has run it.

### When doctor cannot fix it: `--report`

```bash
ryoku doctor --report        # writes ~/.local/state/ryoku/doctor-report.txt
ryoku doctor --report bug.txt
```

The report bundles the findings with system state (disk and snapshot health,
failed units, recent journal errors, package and channel state, session
environment, GPU and display drivers) into one text file to attach to a bug
report. It contains no passwords or keys.

### When you want it to reason: `--explain`

`ryoku doctor --explain` sends that same report to a cloud model and prints its
root-cause analysis and fix steps.

<Warning>
  `--explain` is strictly **advisory and read-only**: it never runs anything, so
  a wrong answer can only mislead. It is opt-in and uses **your own key**;
  nothing is sent unless you set one.
</Warning>

Any OpenAI-compatible endpoint works. Defaults target Groq:

```bash
export RYOKU_AI_KEY=...   # or write it to ~/.config/ryoku/ai-key
ryoku doctor --explain
```

## Window manager

- `ryoku wm status` names the running window manager and its provider;
  `ryoku wm caps` lists what it can do.
- `ryoku wm use <name>` switches window manager: it installs that desktop
  variant if needed, previews anything the target cannot honour, and tells you
  to log out and pick it at the greeter. The one you leave stays installed
  unless you add `--remove-previous`. The **Compositor** tab on the window
  manager page of Ryoku Settings does the same.

## One layout everywhere: `ryoku keyboard`

A keyboard layout has to land in four places: the window manager, the SDDM
greeter, the console, and the boot image, which is what the disk passphrase
prompt uses. The last one is the trap: the keymap is copied in when the boot
image is built, so editing it later never reaches the passphrase prompt.

| Command | What it does |
| --- | --- |
| `keyboard status [--json]` | Each layer's layout, and whether the boot image predates the current keymap. |
| `keyboard detect` | The layout this machine records, and which source said so. |
| `keyboard apply [layout]` | Write the greeter and console keymap, then rebuild the boot image so the passphrase prompt follows. `--no-boot` skips the rebuild. |

With no layout, `apply` pushes the desktop's own layout out, and `doctor`
reports any drift with the exact fix.

## Sign-in: `ryoku keyring` and `ryoku security-key`

`ryoku keyring` chooses how the GNOME keyring unlocks your saved passwords at
sign-in. The default, `never-ask`, means no app ever prompts;
`unlock-on-login` keeps the store encrypted and unlocks it with your login
password; `ask` leaves it locked until an app asks. The Lockscreen page in
Ryoku Settings drives the same choice.

`ryoku security-key` enrolls a FIDO2/U2F key and turns it on for `sudo`,
polkit prompts or login, either instead of the password or together with it.

## Config lay-down: `ryoku materialize`

`ryoku materialize` lays Ryoku's base config into `~/.config` and then overlays
your edits from `~/.config/ryoku/user_edits`, so a file there wins at its
mirrored path. It clobbers the previous Ryoku copy, prunes files a past release
shipped but this one dropped, and never touches files Ryoku never shipped. The
generated display and GPU drop-ins are seeded only when absent. `ryoku update`
and the installer run it for you; on a source checkout use the deploy instead.

## Emergency: `ryoku recovery`

The last resort when the desktop is too broken to update normally. It always
restores the stable channel: it pulls `main`, reinstalls the base packages and
redeploys, **overwriting Ryoku's configs**. It prefers a local copy of
`bin/ryoku-recovery` and otherwise fetches the canonical script, so it still
works when the local build is broken. See [Troubleshoot](/docs/troubleshoot).

## Environment and state

| Variable | What it does |
| --- | --- |
| `RYOKU_REPO` | The checkout root, for `deploy` and a source checkout. |
| `RYOKU_CONFIG_BASE` | Overrides the `materialize` base dir (default `/usr/share/ryoku/config`). |
| `RYOKU_AI_KEY` | Your provider key for `doctor --explain`, or write it to `~/.config/ryoku/ai-key`. |
| `RYOKU_AI_URL` | The API base (default `https://api.groq.com/openai/v1`; for OpenRouter use `https://openrouter.ai/api/v1`). |
| `RYOKU_AI_MODEL` | The model (Groq default `llama-3.3-70b-versatile`). |

State lives under `$XDG_STATE_HOME/ryoku` (default `~/.local/state/ryoku`):

| File | What it is |
| --- | --- |
| `materialized` | The manifest of Ryoku-owned files, so the next `materialize` can prune cleanly. |
| `update-log.txt` | Everything the last update's tools printed. |
| `doctor-report.txt` | The latest diagnostic report. |
| `repo`, `deployed` | The checkout and commit the last deploy laid down (source checkouts). |
