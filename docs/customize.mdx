Most customization happens in **Ryoku Settings** (the Hub), opened with `Mod+,`.
This page is the other half: the plain files Ryoku reserves for you in
`~/.config/`, which `ryoku update` never touches. Reach for them when the GUI
does not cover what you want, or when you would rather edit text than click.

## Make it yours

The knobs most people reach for first live in **Ryoku Settings** (`Mod+,`), and
the [first-run welcome](/docs/first-boot) offers the same handful inline:

- **Interface scale.** If everything looks oversized on first boot, ease the
  interface scale down and the whole shell resizes. This is the single most
  common first-boot fix.
- **The bar.** QS Bar is the default; Orpheus, Sumi, Kairos, Shima, Python and
  Nomarchy are the other styles. **Bar Studio** arranges the rails, zones and
  widgets.
- **Desktop widgets.** Right-click the wallpaper and choose **Edit desktop** to
  add, move and resize widgets, set up depth and parallax, or add a
  visualizer.
- **Colors.** The palette follows your wallpaper by default (derived by
  `matugen`), so a new wallpaper recolors the whole desktop; lock a fixed
  palette instead if you prefer. See [Theming](/docs/theming).

Deeper window work (rounding, blur, gaps, animations) stays in Ryoku Settings
too. This page picks up where the GUI stops.

## Personal compositor overrides

Each window manager reads one file of yours last, so it wins over both the
shipped defaults and anything Ryoku Settings writes. It is seeded once and never
touched by `ryoku materialize` or an update.

<Tabs>
  <Tab title="Hyprland: user.lua">
    `~/.config/hypr/user.lua` loads last. The order, from
    `ryoku/hyprland/hyprland.lua`, is:

    1. `modules.env`, then `keyboard.lua`.
    2. The generated drop-ins `gpu.lua` and `monitors.lua`, then your
       `monitors_user.lua` if present.
    3. The base modules (`displays`, `input`, `touchpad`, `decoration`,
       `animations`, `binds`, `window_rules`, `autostart` and the rest).
    4. `settings.lua`, written by the Hub.
    5. The power saver, when Performance follows the power profile.
    6. `user.lua`: yours, loaded last, wins.

    ```lua
    -- ~/.config/hypr/user.lua
    hl.bind("SUPER", "U", "exec, kitty -e htop")
    hl.windowrule("float", "class:^(pavucontrol)$")
    ```

    Use the `hl` API the modules use (`hl.bind`, `hl.windowrule`, the keyword
    setters) rather than shelling out to `hyprctl`.
  </Tab>
  <Tab title="niri: user.kdl">
    `~/.config/niri/user.kdl` is the last include in `config.kdl`. Before it
    come the machine seeds (`keyboard.kdl`, the generated `gpu.kdl` and
    `monitors.kdl`, your `monitors_user.kdl`), then the Hub's generated
    `settings.kdl` and `rebinds.kdl`. The last include wins for a value set
    twice, and a chord you bind here replaces the shipped one.

    ```kdl
    // ~/.config/niri/user.kdl
    binds {
        Mod+Shift+T { spawn "kitty"; }
    }
    ```

    Never hand-edit `settings.kdl` or `rebinds.kdl`; they are rewritten from
    the Hub.
  </Tab>
</Tabs>

## Manual monitor pinning

For everyday display changes, use **Settings > Displays** (see [Displays &
hardware](/docs/hardware)). It writes the generated `monitors.lua` (Hyprland)
or `monitors.kdl` (niri), which `ryoku-monitor` also rewrites once per machine
and on hotplug or GPU reset.

When you need a layout the page cannot express, a fake-EDID display that needs
a forced mode, a forced modeline, or a specific position, write
`~/.config/hypr/monitors_user.lua` or `~/.config/niri/monitors_user.kdl`
instead. It loads after the generated file, so your pins win, and updates never
touch it. On Hyprland a template ships at
`~/.config/hypr/monitors_user.lua.example`.

## Per-app settings

Each app under `ryoku/apps/<app>/` keeps its native format under its own
directory; there is no Lua wrapper for a tool that reads its own config. Where an
app ships a base file, drop your changes in the paired override file so an update
cannot clobber them:

| App | Shipped file | Override file |
| --- | --- | --- |
| Kitty | `~/.config/kitty/kitty.conf` | `~/.config/kitty/user.conf` |
| Fish | `~/.config/fish/config.fish` | `~/.config/fish/user.fish` |
| Starship | `~/.config/starship.toml` | edit in place |
| Neovim | `~/.config/nvim/` | LazyVim's own override paths |
| Yazi | `~/.config/yazi/yazi.toml` | edit in place |
| Fastfetch | `~/.config/fastfetch/` | edit in place |

## What survives an update

[`ryoku materialize`](/docs/cli#config-lay-down-ryoku-materialize) clobbers the
files Ryoku ships and prunes files a past release shipped but this one dropped.
It **never touches** files Ryoku only seeds once or never shipped, which is
what makes `user.lua`, `user.kdl`, the `monitors_user` files,
`kitty/user.conf`, `fish/user.fish` and your own additions survive every
update. Changes you make in Ryoku Settings are kept in
`~/.config/ryoku/user_edits` and laid back over the shipped config on every
update.

The generated drop-ins (`monitors` and `gpu`) are seeded only when absent and
are never clobbered or pruned, so an update never resets your display layout or
GPU pin.

<Warning>
  Editing a shipped file in place (anything in the "shipped file" column above,
  or `hypr/hypridle.conf`, and the other base configs) is reset on the next
  `ryoku materialize`. Put lasting changes in an override file, or in your
  `user.lua` or `user.kdl`.
</Warning>

## Reloading after a change

After editing a file by hand:

```bash
ryoku reload
```

This restarts the shell and reloads the window manager. Ryoku Settings applies
its own changes live and does not need a reload.
