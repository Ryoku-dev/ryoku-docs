How to work in the [Ryoku repository](https://github.com/Ryoku-dev/ryoku): the
dev loop, the gates a commit passes, the path a change takes from the repo to a
user's machine, and where new code belongs.

The in-repo guides are the source of truth and override anything that drifts
here: [`AGENTS.md`](https://github.com/Ryoku-dev/ryoku/blob/main/AGENTS.md),
[`CONTRIBUTING.md`](https://github.com/Ryoku-dev/ryoku/blob/main/CONTRIBUTING.md),
[`docs/development.md`](https://github.com/Ryoku-dev/ryoku/blob/main/docs/development.md)
and [`docs/updates.md`](https://github.com/Ryoku-dev/ryoku/blob/main/docs/updates.md).

## The dev loop

Ryoku is developed on a running Ryoku machine. Edit the repo, deploy, test on
the running system. Never edit `~/.config` directly and copy it back; the flow
is repo to system only.

```bash
ryoku/shell/dev-run.sh       # build ryoku-shell and run it from the checkout (hot reload)
ryoku/shell/dev-binds.sh on  # bind the shell keys to the dev shell for this session
ryoku/shell/dev-stop.sh      # stop the dev shell
ryoku/shell/deploy.sh        # lay the repo into ~/.config and rebuild the binaries
```

`dev-run.sh` leaves your own `~/.config` alone. On an installed system the same
config arrives through `ryoku materialize`, which lays the base config in from
the packages; the `ryoku` command detects which world it is in.

## How a change reaches a user

A dev box runs the checkout; users run packages. Where a change lives decides
how it gets there.

| Change | Vehicle |
| --- | --- |
| Desktop config and binaries (`ryoku/`) | Signed packages, then `ryoku materialize` re-lays the base config on the next `ryoku update`. User edits live in `~/.config/ryoku/user_edits` and survive. |
| A new default app or package | The edition's package set for new installs, and the provisioning manifest so existing installs receive it once. Apps a user left out stay out. |
| The installers (`installation/`, `ryoku-shell-installer/`) | New installs only. A change to the script installer means rebuilding its committed binary and checksum. |
| Stateful drift nothing above can express | An idempotent `ryoku doctor` reconciler, which runs inside every `ryoku update`. |

There is no ordered migration ledger. A removed or renamed `shell.json` key
needs a doctor reconciler, and `bin/ryoku-dev-verify-delivery` checks that
every shipped config reaches users.

## Where new code goes

| Intent | Where it goes |
| --- | --- |
| A package every machine should have | The matching set in `system/packages/`, plus its rows in the Void and Fedora translation tables. Prefer official repositories over the AUR. |
| A keybind | The neutral catalogue in `ryoku/wm/binds.go`; each compositor provider renders it. |
| A compositor concern | That compositor's own config: Lua modules under `ryoku/hyprland/`, KDL under `ryoku/niri/`. Nothing outside `ryoku/wm/` names a compositor; the desktop asks capabilities. |
| A shell surface | A component under `ryoku/shell/quickshell/`, with its state wired through `ryoku-shell` (`ryoku/shell/ipc/`). QML renders; the Go daemon decides. |
| A Ryoku Settings page or control | The Hub under `ryoku/hub/`, with the logic in its Go backend. |
| A doctor reconciler | A file under `ryoku/cli/internal/doctor/`, registered in its list. Idempotent, cheap to check, safe to repeat. |
| A new app's native config | `ryoku/apps/<app>/` in the tool's own format. Never a Lua wrapper for a tool that reads its own config. |
| A new `[ryoku]` package | `release/packages/<name>/`, with its Fedora spec and Void template beside the other editions' builds. |

## Verify before committing

Test behavior on the running system, not only that a file parses:

- **Lua:** `luac -p <file>`.
- **Shell scripts:** `bash -n <file>`; `shellcheck` runs on push.
- **QML:** `qmllint`, and `bin/ryoku-dev-lint-qml` on a dev box.
- **Go:** `go build ./... && go vet ./... && go test ./...` in each module you
  touched.
- **Installer:** run the backend with `RYOKU_DRYRUN=1` to print every action
  without touching a disk.
- **The seam and delivery:** `bin/ryoku-dev-verify-wm-isolation` and
  `bin/ryoku-dev-verify-delivery`.

## Commits

Every commit passes the hooks in `.githooks/`; install them with
`bin/ryoku-dev-install-hooks`. **Never use `--no-verify`.**

- The subject is `[area] scope: imperative summary`, 72 characters or fewer,
  no trailing period. The area is one of `global`, `installation`, `system`,
  `ryoku`, `docs`, `test`, `tooling`, `release`.
- No em-dash anywhere, no authorship or attribution trailers, no filler.
- One logical change per commit, with the matching `CHANGELOG.md` entry.
- Anything a user would notice gets a plain-language trailer that the release
  bot collects into the release notes:

```text
Note: New: pin an app by right-clicking it in the dock
Note: Fixed: right-clicking a dock app now saves or removes the pin
Note: Removed: the old instant-replay buffer
```

## Branches

Work goes to `unstable-dev`. Every push there runs the **Testing gate**, which
waits for the required checks and then records the commit for testers on
`ryoku track unstable`; the package publishers run the same gate before they
upload the testing repositories. `main` only moves by a fast-forward from
`unstable-dev` when a release is ready, and a release is the **Stable Release**
workflow run on `main`. See [Release pipeline](/docs/release-pipeline).

## Writing prose

- **No em-dash.** Use a comma, a colon, a period or parentheses.
- **No emoji, no marketing fluff.** Plain, direct, technical prose.
- **Match the files next to yours.** When in doubt, copy the closest neighbour.
- **Comment the *why* when it is not obvious.** Never narrate the *what* or
  leave commented-out code.
