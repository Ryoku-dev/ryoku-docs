title: Release Pipeline
description: How a commit becomes a testing build, how a release becomes signed packages and ISOs, and how to verify them.

Ryoku ships three kinds of artifact, all signed with the same release key:

- **Package repositories** at `repo.ryoku.dev`: the pacman `[ryoku]` repository
  for Arch and CachyOS, an XBPS repository for Void, and an RPM repository for
  each supported Fedora release.
- **Live ISOs** for Arch, CachyOS and Void
  ([/docs/iso-build-recipe](/docs/iso-build-recipe)).
- **The script installer**, a prebuilt binary committed in
  `ryoku-shell-installer/` with its checksum.

Everything is built from the monorepo by scripts under `release/`,
`installation/iso/` and `void/iso/`, and published by the workflows under
`.github/workflows/`. The in-repo
[`docs/development.md`](https://github.com/Ryoku-dev/ryoku/blob/main/docs/development.md)
("Branches and pushing") is the authoritative sequence.

## Versioning

`VERSION` at the repo root holds the tracked version, and `CODENAME` names the
current release line (its story lives in `release/names.md`). The release
helpers under `bin/` derive every other form from them, including the
per-build package version, so every published build is strictly newer than the
last. After each push to `unstable-dev`, the **Unstable Version Bump** workflow
advances the unstable build number with a bot commit.

## Channels

| Channel | Fed by | Path under `repo.ryoku.dev/stable/` |
| --- | --- | --- |
| **testing** | every push to `unstable-dev` that passes its checks | `channels/testing/...` |
| **stable** | a release tag | the edition's root (`x86_64/`, `void/`, `fedora/<N>/`) |

A release tag builds the set once into `releases/<tag>/`, a frozen copy that is
never overwritten, and only then copies it over the stable pointer. That frozen
history is what `ryoku rollback --to` and `ryoku track <version>` move between.
The **Release Ledger** workflow rebuilds the release indexes the Hub and the
website read. A scheduled retention worker (`release/r2-retention/`) keeps the
ten newest package snapshots per edition and channel, and the ten newest ISOs
per variant.

## From a commit to testers

1. A commit lands on `unstable-dev`. The required checks run: Go unit tests,
   the installer backend tests, the delivery check and QML lint, among others.
2. The **Testing gate** waits for all of them and records the commit in
   `channels/testing/checked.json`. Boxes on `ryoku track unstable` build that
   commit from source on their next `ryoku update`.
3. The publishers (`publish-repo.yml`, `publish-repo-void.yml`,
   `publish-repo-fedora.yml`) run the same gate, then build, sign and upload the
   testing repositories. A red check never reaches a channel.

## Cutting a release

1. `main` advances only by a fast-forward from `unstable-dev`, pushed with
   `RYOKU_RELEASE_PUSH=1 git push origin unstable-dev:main`. The `pre-push` hook
   refuses any other push to `main`.
2. The **Stable Release** workflow runs on `main`. With `bump_type: none` it tags
   the version `main` already carries; `patch`, `minor` and `major` bump first.
   It commits and tags the release, then dispatches the repository publish and
   the release notes.
3. The **Release Notes** workflow collects every `Note: New|Fixed|Removed:`
   trailer between the previous tag and this one into the GitHub release. Never
   squash-merge into a release branch: squashing drops the notes.
4. The ISOs are built by dispatching `build-iso.yml`, `build-iso-cachyos.yml`
   and `build-iso-void.yml` with the release stage. Each build signs the ISO,
   writes its checksum and manifest, and uploads them beside the public key.

## Building the pacman repository

`release/repo/build-repo.sh` is the local and CI builder. It runs every
`release/packages/*/PKGBUILD` with `makepkg --sign`, confirms each package has
a signature beside it, builds the signed database with `repo-add -s`, and
writes the bare `ryoku.db` and `ryoku.files` names as real files, because
object storage has no symlinks. `--nodeps` is deliberate: only the host build
toolchain matters at build time. The Void and Fedora publishers build the same
packages from their templates and specs.

## The signing key

The release identity is `Ryoku Releases <releases@ryoku.dev>` with fingerprint
`EB6D3C0F55A7B3CABA6B2838847B274F025DD6E3`. The canonical public key lives in
the repo at `keys/ryoku-release-key.pub.asc`, and the `ryoku-keyring` package
carries it into pacman's keyring.

To rotate the key: regenerate the keyring files, bump the `pkgver` date in
`ryoku-keyring`, replace `keys/ryoku-release-key.pub.asc`, and update the
fingerprint the builders sign with.

## Verifying a published ISO

```bash
gpg --import keys/ryoku-release-key.pub.asc
gpg --fingerprint releases@ryoku.dev

gpg --verify ryoku-<date>-x86_64.iso.sig ryoku-<date>-x86_64.iso
sha256sum -c ryoku-<date>-x86_64.iso.sha256
```

The fingerprint MUST match `EB6D3C0F55A7B3CABA6B2838847B274F025DD6E3` before
you trust the imported key.
